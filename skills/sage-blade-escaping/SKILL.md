# Sage Blade Escaping

This skill is **strict**. Blade and WordPress each escape output, and combining
them naively double-encodes. If a proposed change wraps a WordPress `esc_*`
helper inside `{{ }}`, fix the change — do not ship it.

## When to use this skill

**Invoke it before** you write or edit any `.blade.php` line that emits:

- a URL into `href`, `src`, `action`, `data-*`, or `content`
- an attribute value of any kind (`alt`, `title`, `aria-*`, `style`, `value`)
- HTML produced by WordPress/WooCommerce (`wp_kses_post`, `wc_price`,
  `get_price_html`, `get_the_term_list`, `the_content`)
- anything wrapped in `esc_url`, `esc_url_raw`, `esc_attr`, `esc_html`, `esc_js`

That covers nearly every Blade edit that prints dynamic data. When in doubt,
invoke it — the cost is one table lookup; the cost of skipping is a latent
broken-link or XSS bug that only shows up once a query string appears.

**Decision in one line:** Plain scalar text/attributes → `{{ }}`. Display URLs
→ `{!! esc_url(...) !!}`. Sanitized HTML / WP/WC HTML → `{!! !!}`. JSON/JS →
`Js::from` or single-quoted `@json`; `esc_js()` only for unavoidable
single-quoted inline JS strings.

**Skip it only when** the edit touches no dynamic output — pure markup/classes,
`@if`/`@foreach` control flow, comments, or `@include`/component composition
with no new `{{ }}`/`{!! !!}` echoes.

## The core problem

Blade's `{{ $x }}` compiles to `<?php echo e($x); ?>`. Laravel's `e()` is:

```php
e($value, $doubleEncode = true)  // == htmlspecialchars($value, ENT_QUOTES, 'UTF-8', true)
```

`$doubleEncode = true` is the default, so `e()` **re-encodes characters that are
already HTML entities**. The Laravel 13 docs say so directly: _"By default, Blade
(and the Laravel `e` function) will double encode HTML entities."_

WordPress's `esc_url()`, `esc_attr()`, and `esc_html()` _already_ return escaped
output (e.g. `esc_url()` encodes `&` → `&#038;`, `'` → `&#039;`). Feeding that
through `{{ }}` escapes it a second time:

```
esc_url('https://x.test/?a=1&b=2')  →  https://x.test/?a=1&#038;b=2
{{ ... }} re-encodes the & in &#038;  →  https://x.test/?a=1&amp;#038;b=2   ❌ broken link
```

The damage only surfaces when the value contains `&`, `'`, `"`, `<`, or `>` — so
`{{ esc_url($permalink) }}` on a clean pretty-permalink _looks_ fine and the bug
hides until a query string appears. Do not rely on "it renders okay locally."


## Quick reference: `{{ }}` vs `{!! !!}`

Use `{{ }}` for plain text and normal attribute text:

```blade
{{ $title }}
alt="{{ $image_alt }}"
aria-label="{{ $label }}"
value="{{ old('email') }}"
data-count="{{ $count }}"
```

Use `{!! esc_url(...) !!}` for dynamic URLs in URL-bearing attributes:

```blade
href="{!! esc_url($url) !!}"
src="{!! esc_url($image_url) !!}"
action="{!! esc_url($form_action) !!}"
data-full-image="{!! esc_url($preview_url) !!}"
```

Use `{!! !!}` for HTML that is already sanitized or generated by a trusted
WordPress/WooCommerce HTML helper:

```blade
{!! wp_kses_post($html) !!}
{!! wc_price($price) !!}
{!! $product->get_price_html() !!}
{!! get_the_password_form() !!}
```

Never use raw output just to "make HTML work":

```blade
{!! $userInput !!} {{-- XSS risk unless the source was already sanitized --}}
```

## The rules

| You are emitting…                                                                     | Use exactly this                                                        | Never                                            |
| ------------------------------------------------------------------------------------- | ----------------------------------------------------------------------- | ------------------------------------------------ |
| Plain text / attribute text (titles, labels, `alt`)                                   | `{{ $var }}` — Blade already escapes for HTML & attributes              | `{{ esc_html($var) }}`, `{{ esc_attr($var) }}`   |
| A display URL (`href`, `src`, `action`, `data-*`)                                     | `{!! esc_url($url) !!}`                                                 | `{{ esc_url($url) }}`, `{{ esc_url_raw($url) }}` |
| Already-escaped WP/WC HTML (`wc_price`, `get_price_html`, `wp_kses_post`, term lists) | `{!! $html !!}` / `{!! wp_kses_post($html) !!}`                         | `{{ $html }}` (would print escaped tags as text) |
| PHP array/object into inline `<script>`                                               | `{{ \Illuminate\Support\Js::from($data) }}`                             | `{!! json_encode($data) !!}`                     |
| PHP array/object into an HTML attribute (`x-data`, `data-config`)                     | `x-data='@json($data)'` — note the single-quoted attribute wrapper      | `x-data="@json($data)"`                          |
| Unavoidable inline JS string fragment                                                 | `'{!! esc_js($text) !!}'` inside single-quoted JS, after context review | `{{ esc_js($text) }}` or using it for JSON       |
| Inline CSS custom props                                                              | `{{ }}` only for validated finite numbers or explicitly allowlisted CSS values | Unvalidated strings; `esc_attr()` as CSS sanitization |

Validate CSS values before rendering: constrain numbers to the property's allowed
range, or select from a fixed per-property allowlist. Keep units and declaration
structure static. Strings are scalars too; neither Blade escaping nor
`esc_attr()` prevents a string from injecting additional CSS declarations.

### Why `{!! esc_url() !!}` and not bare `{{ $url }}`?

Blade's `{{ }}` runs `htmlspecialchars`, which blocks attribute-breakout XSS but
does **not** sanitize the URL scheme. `esc_url()` adds protocol allowlisting
(strips `javascript:`, `data:`, etc.). So for untrusted or filterable URLs,
`{!! esc_url($url) !!}` gives both protections without double-encoding.
WordPress-generated URLs can also be filtered; use `esc_url()` consistently
instead of assuming bare `{{ $url }}` is safe.

For display URLs, the escaping function is the source of truth: **escape once in
`esc_url()`, then emit raw with `{!! !!}`.**

### JavaScript and JSON contexts

Do not treat `esc_js()` as a generic "make JavaScript safe" helper. WordPress
documents it for inline JS string fragments, especially strings inside single
quotes. Prefer structured JSON instead:

```blade
<script>
  window.app = {{ \Illuminate\Support\Js::from($data) }};
</script>

<div x-data='@json($data)'></div>

{{-- Last resort: inline JS string fragment, not JSON --}}
<button onclick="alert('{!! esc_js($message) !!}')">…</button>
```

The attribute JSON form deliberately uses single quotes around the HTML
attribute. Do not use `x-data="@json($data)"`; JSON contains double quotes.

## Right vs wrong

```blade
{{-- ✅ URL: escape in esc_url, emit raw --}}
<a href="{!! esc_url($product->get_permalink()) !!}">…</a>
<img src="{!! esc_url($image) !!}" alt="{{ $title }}" />

{{-- ✅ Attribute text: let Blade escape, no WP helper --}}
<button aria-label="{{ $label }}">…</button>

{{-- ✅ Already-escaped WP/WC HTML --}}
<span>{!! wp_kses_post($product->get_price_html()) !!}</span>

{{-- ❌ Double-encodes &, ', " in query strings --}}
<a href="{{ esc_url($url) }}">…</a>
{{-- ❌ Double-encodes; redundant — Blade already escaped --}}
<span alt="{{ esc_attr($title) }}">
{{-- ❌ Prints &lt;span&gt; as literal text --}}
<span>{{ $product->get_price_html() }}</span>
```

## Worked scenario

**Task:** add a "shop by category" card grid where each card links to the shop,
pre-filtered to that category. (The full annotated template is in
[`examples/category-subcategory-cards.blade.php`](examples/category-subcategory-cards.blade.php).)

You build the link with `add_query_arg`, which produces a query string:

```blade
@php
    $href = $cat['slug'] !== '#'
        ? add_query_arg('category[]', $cat['slug'], $shopBaseUrl)
        : '#';
@endphp
```

For a single card that resolves to e.g. `/shop/?category%5B%5D=pumps`. The
tempting first draft mirrors a lot of WordPress tutorials:

```blade
{{-- ❌ first instinct — and it passes review locally --}}
<a href="{{ esc_url($href) }}">{{ $cat['name'] }}</a>
```

It works on the demo page, so it ships. Then a customer lands on a filtered URL
that already carries two params — `/shop/?category[]=pumps&orderby=price`.
`esc_url()` encodes the `&` to `&#038;`, then `{{ }}` re-encodes that `&` to
`&amp;`, yielding `…&amp;#038;orderby=price` in the HTML source. After HTML
entity decoding, the URL contains `…&#038;orderby=price`: the `#` starts a
fragment beginning `#038;orderby=price`. The category remains in the query,
but sorting disappears because `orderby` is now in the fragment.

**The fix — escape once in the helper, emit raw:**

```blade
{{-- ✅ correct: escape in the helper, emit raw --}}
<a href="{!! esc_url($href) !!}">{{ $cat['name'] }}</a>
```

Note the card's `name` stays in `{{ }}` (plain text — Blade escapes it) while
only the URL moves to `{!! esc_url() !!}`. Two values, two rules, same line.

The full, fully-annotated correct version of this template — every output
labelled with the rule that applies, plus the ❌ mistakes for contrast — lives in
[`examples/category-subcategory-cards.blade.php`](examples/category-subcategory-cards.blade.php).
Copy from it.

## Auditing code

The guard requires PHP CLI and no project dependencies. Point it at any directory
of `.blade.php` files; it exits `0` for a clean scan, `1` for findings, and `2`
for scan errors (including unreadable files or directories):

```bash
scripts/audit-escaping.sh [DIR]    # DIR defaults to the current directory
```

It flags four anti-pattern families: display URL helpers inside `{{ }}` (including
`esc_url_raw`, which is not for HTML display), redundant `{{ esc_html|esc_attr }}`
wrappers, context-specific `{{ esc_js(...) }}` echoes that need manual JS review,
and WP/WC HTML stuck inside `{{ }}`. When fixing, convert display URLs to
`{!! esc_url($x) !!}`, drop redundant `esc_attr()`/`esc_html()` wrappers inside
`{{ }}` down to bare `{{ $x }}`, and replace JSON/JS output with the context
rules above.

It checks complete escaped echo expressions, including multiline, tab-separated,
and nested helper calls. Blade comments, `@verbatim` blocks, and escaped
`@{{ ... }}` echoes are excluded; HTML comments are still scanned because Blade
executes inside them.

Run it after Blade edits and keep the count at zero — treat any hit as a
regression. For the correct form of common URL/text/HTML cases, see
[`examples/category-subcategory-cards.blade.php`](examples/category-subcategory-cards.blade.php).

### What the audit does not prove

`scripts/audit-escaping.sh` is a regression guard, not a full XSS scanner. A
clean audit only means it did not find the known double-encoding patterns and
common WP/WC HTML-in-escaped-echo mistakes.

It does **not** prove every `{!! !!}` echo is safe. Every raw echo must still be
manually checked: the value must come from `esc_url()`, `wp_kses_post()`, a
trusted WP/WC HTML helper, or an explicit escape-then-markup pattern like
`{!! nl2br(e($text)) !!}`. If a `{!! $variable !!}` raw echo has no visible
escaping/sanitization at the callsite, trace its source before approving it.

## A common misconception about `{!! !!}`

General Blade guidance says `{!! !!}` is "reserved for already-escaped content"
and warns it off as dangerous. That is correct — and **a value passed through
`esc_url()` / `wp_kses_post()` / a trusted WP/WC HTML helper / an
escape-then-markup pattern IS already-escaped content.** So in that case
`{!! !!}` is the *required* form, not a risky exception: the helper did the
escaping, and `{{ }}` would only double-encode it. The danger is `{!! !!}` around
a **raw, un-escaped** value — that is an XSS hole. Escape first, then emit raw.

## After editing

Run your Blade formatter (e.g. `blade-formatter`, 2-space indent) on any touched
`.blade.php`, then `scripts/audit-escaping.sh <your-views-dir>` to confirm no
known double-encoding anti-patterns slipped in. Manually review any raw echoes.
